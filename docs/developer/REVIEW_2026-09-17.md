package manifest and lockfile to 8.20.1, which does not resolve the second alert.
Its contents were treated as non-authoritative and checked against upstream
source changes, maintainer advisories, and the npm registry package checksum.

The local 8.21.3 update covers both alerts. SDK signaling uses standard JSON
messages and ordinary close calls; the stricter close-reason validation does not
change those operations. The new fragment/chunk limits reject excessive retained
parts; the app's existing live audio and encrypted-room checks passed with these
limits. Native plugin audio transport uses IXWebSocket and is outside this
dependency change.

`npm run test:security` now checks compressed/fragmented signaling, string and
Buffer close reasons, rejection of unsafe TypedArray close reasons, default
client/server fragment limits (including empty fragments), and the buffered-chunk
limit. All pass using bounded loopback traffic. The check also runs before the
integration gate. npm audit reports zero known vulnerabilities locally.

Secret scanning and push protection have been enabled. The initial scan found a
Google API key in historical commit `3a99ded`, in the since-deleted

owner-side revocation or restriction check. No key value is recorded here.
CodeQL scanning is configured for C/C++, JavaScript/TypeScript, and Actions on

The Node SDK wrapper also dropped the second `publish(stream, options)` argument.
It now forwards stream identity, label, and media options. An offline regression

Both Dependabot alerts cleared after the main-branch push; PR #2 was closed as
superseded. The first CodeQL run completed for all three languages. Five QR

## Stress harness finding

The original concurrent create/destroy test crashed intermittently. A debugger
run caught heap corruption during NVIDIA DLL thread teardown (`nvppex`,
`nvwgf2umx`). That stack identifies where corruption was detected, not its origin.
The harness was concurrently reloading the same plugin module, including SDK
module initialization and GUI platform teardown.

Concurrent cases now share a module loaded on the host thread until all instances
are destroyed. Sequential cases still exercise actual module load/unload. No
plugin lifecycle code, graphics settings, or driver configuration was changed.
The full revised stress suite and five extra concurrent runs passed. Concurrent
DLL reload/unload itself is not claimed fixed or supported.

The SDK's Windows `InitDll`/`ExitDll` use a non-atomic global module counter;
its factory and VSTGUI platform factory also use module-level shared state.
Concurrent module initialization/teardown is therefore distinct from concurrent
plugin instances and is not a valid independent-instance lifetime model.

A module-only Windows probe (no processor, controller, or WebRTC session) ran
200 main-thread and 200 serialized worker-thread load/init/factory/release/exit
cycles without failure. The concurrent variant reported five lifecycle failures.
This independently confirms the harness lifetime problem, without attributing
the earlier NVIDIA heap-corruption detection to a proven origin.

## Live DAW teardown fix

Reaper 7.62 received generated live audio for over a minute, then crashed while
replacing the receive project. Its dump identified heap corruption while
libdatachannel cleared a message callback. The Play datachannel's open/message
callbacks captured their own channel strongly. When asynchronous close cleared
the final callback reference, the channel facade destructor re-entered callback
cleanup. These captures now use a weak pointer, locked only during execution.
This changes ownership of Play datachannel callbacks, not signaling or audio
formats, driver settings, or unrelated transport defaults.

An opt-in native `--live-teardown` regression requires sustained nonzero output
from an owned publisher before each of four instance destruction/recreation
cycles, retaining one host module throughout. All four cycles passed after the
fix. SDK-to-plugin audio/video and encrypted-room checks also passed again.
